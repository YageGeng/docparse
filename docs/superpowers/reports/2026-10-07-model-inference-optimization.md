# 模型推理性能优化报告

日期：2026-10-07
对应设计：`docs/superpowers/specs/2026-10-06-model-inference-optimization-design.md`
对应计划：`docs/superpowers/plans/2026-10-06-model-inference-optimization.md`

## 1. 结论

最终方案：

- 使用 `--features tensorrt` 构建：版面检测、OCR（检测/识别/方向）、TATR、表格单元格检测和 Texo 编码器走 TensorRT，CUDA 作为回退；TensorRT 无法构建的图（Texo 解码器、PP-FormulaNet、SLANet+/SLANeXt）保持 CUDA；
- Texo 推理 worker 从 8 个降到 4 个；
- 版面检测每批处理 4 页；
- 配置 `runtime.tensorrt_cache_dir`。

在 gpuhub 上使用生产配置、18 篇真实文档，与基线交替运行 2 轮，结果如下：

| 指标 | 基线 | 最终方案 | 变化 |
| --- | --- | --- | --- |
| 吞吐 c4（页/s） | 6.39 | 7.68 | +20% |
| 吞吐 c2（页/s） | 4.30 | 4.94 | +15% |
| p95 c4 | 14.9 s | 12.5 s | −16% |
| p95 c2 | 12.7 s | 10.8 s | −15% |
| Texo 编码器（生产中 ms/个） | 22.4 | 0.94 | −96% |
| Texo 解码器（生产中 ms/个·步） | 0.21 | 0.07 | −67% |
| 版面检测（生产中 ms/页） | 148.6 | 20.4 | −86% |
| 表格单元格（生产中 ms/表） | 258 | 41.8 | −84% |
| 表格结构 TATR（生产中 ms/表） | 315 | 37.3 | −88% |

质量与稳定性：

- 与基线相比的一致率：区块 0.9994，公式 LaTeX 完全一致 0.96（编辑相似度 0.984），表格结构 0.91–0.96，块文本 0.997。基线与自身对比的波动区间为：公式 0.9995–1.0，表格 0.95–1.0。
- TensorRT 带来的数值差异超出了严格标准；用户确认接受这一差异（见第 5 节）。
- 每轮有 1 个公式因生成到 1024 token 仍无结束符而被拒绝。该公式在基线中的输出本身就是乱码（`\psi^{\perp}(\alpha,q;x,y) ~ ~ ~ …`，共 2055 个字符），因此不属于真实的质量损失。
- 任务失败、显存不足均为 0。

## 2. 关键发现

1. **生产中的耗时主要来自并发争用，而不是模型计算本身。** Texo 编码器单独测量时 batch 16 只需 22 ms，生产中却是 323 ms，相差约 15 倍。把 worker 从 8 降到 4 后，吞吐不变，所有模型在生产中的耗时下降 31–71%。
2. **基准测试必须隔离宿主机噪声。** gpuhub 是多租户机器。同一个二进制、同一份配置，两次端到端运行的吞吐相差可达 24%，单个模型的耗时相差 30–50%。因此：
   - 主要用每个模型的独立微基准（中位数）判断模型自身的提速；
   - 端到端测试只用于验证质量和稳定性，并且必须与基线交替成组运行。
3. **TensorRT 必须使用显式形状档位（profile）。** 只靠隐式动态形状时，每遇到更大的 batch，TensorRT 就要花几分钟重建引擎。预热轮次因此只有 0.19 页/s，1784 个公式超时。改为每个模型声明“batch 从 1 到配置的 batch_size，各维度的范围”之后，引擎在启动时一次构建完成，运行期间不再重建。
4. **TensorRT 引擎每次构建的数值都有细微差异。** 它按计时结果选择 kernel，不同构建之间公式一致率在 0.954 到 0.993 之间波动。关闭 TF32 不能消除这种差异。

## 3. 逐模型、逐级结果

### 3.1 独立微基准（中位数，3 轮交替）

| 模型 | CUDA FP32 | 卷积穷举搜索 | NHWC | TF32 | FP16 模型 | TensorRT |
| --- | --- | --- | --- | --- | --- | --- |
| Texo 编码器 b16 | 22.7 ms | −1% | +25% | −2% | −37%（质量不过） | **15.9 ms（−32%）** |
| 版面检测 b1 / b4 | 32.8 / 104.6 ms | +1% | +9% | 0% | −20%（质量不过） | **b4 58.9 ms（−44%）** |
| 表格单元格 b1 | 11.0 ms | −1% | −1% | −25% | ≈TF32 | **4.83 ms（−43%）** |
| TATR b1（600×800） | 8.2 ms | — | +57% | −1% | +11% | **3.3 ms（−60%）** |
| Texo 解码器 b20（每步） | 1.68 ms | — | — | −1% | 无法转换 | 初始化失败 |

版面检测的批大小：b1 32.9 ms/页，b2 27.3 ms/页（−17%），b4 25.9 ms/页（−21%）。

### 3.2 各级结论

- **第 0 级：并发调优（采纳）。** Texo worker 从 8 降到 4，吞吐持平或提升，各模型耗时下降 31–71%，质量与基线一致。
- **第 1 级：CUDA 参数。** 微基准中单元格模型开 TF32 后 −25%。**更正**：复核发现 ONNX Runtime 的 CUDA provider 默认就启用 TF32（在 ORT 1.29 上实测：不设置 `use_tf32` 时生效值为 1），生产 CUDA 构建一直在用 TF32；微基准的代码已随清理删除，无法再确认其对照组是否显式关闭了 TF32。因此这 25% 不是相对生产的收益。配置项 `tf32` 改为默认 `true`（与 ORT 一致，行为不变），设为 `false` 可对单个模型强制完整 FP32。卷积穷举搜索和 NHWC 没有收益或变慢，未采纳，也不提供配置项。
- **第 2 级：版面检测按批处理（仅与 TensorRT 搭配）。** 在 CUDA 上用 batch 4 时显存耗尽，所有表格识别失败。TensorRT 引擎占用的显存更少，可以正常使用。
- **第 3 级：FP16（全部放弃）。**
  - 版面检测转 FP16 后区块位置偏移，导致下游公式一致率降到 0.896、表格降到 0.83。
  - 编码器转 FP16 后有 11 个公式结果改变，1 个公式卡死。
  - 只把卷积转成 FP16 时没有提速；TATR 转 FP16 反而更慢；解码器无法转换。
  - 相关代码已全部撤回。
- **第 4 级：TensorRT（采纳，按 feature 统一启用）。** 解码器的合并图含 `If` 分支，TensorRT 初始化时会报拓扑排序错误，因此解码器保持 CUDA。非生产模型的验证结果见 3.3 节：PP-FormulaNet 与 SLANet+/SLANeXt 同样无法构建引擎，保持 CUDA。

### 3.3 非生产模型的 TensorRT 冒烟验证

终审指出 OCR、PP-FormulaNet、SLANet+/SLANeXt 和有线单元格检测从未在 TensorRT 下运行过，因此在 gpuhub 上补做了两项验证。

**逐模型构建引擎**（ORT Python 1.29 + TensorRT 10.16，档位与 Rust 代码一致，并断言首个 provider 为 TensorRT，防止静默回退到 CUDA）：

| 模型 | 结果 | 引擎构建耗时 |
| --- | --- | --- |
| OCR 检测（档位上限 4×3×2048×2048） | 通过 | 299 s |
| OCR 识别（宽度上限 3200） | 通过 | 62 s |
| OCR 方向分类 | 通过 | 30 s |
| 有线单元格检测 | 通过 | 113 s |
| PP-FormulaNet S/M/L | 失败：ORT 划分子图（`GetSupportedList`）时报错，与 Texo 解码器相同 | — |
| SLANet+、SLANeXt 有线/无线 | 失败：自回归 `Loop` 不满足 TensorRT 的 `IRecurrenceLayer` 形状校验 | — |

失败的模型若带档位，会让整个 TensorRT 构建在启动时报错退出。因此它们不再声明档位，保持 CUDA；PP-FormulaNet 的 TensorRT 档位和 feature 已一并删除。

**端到端冒烟**（CLI，OCR 设为 `always`，3 篇文档：表格、公式、扫描件；3 组模型组合：PP-S + SLANet+ + 无线单元格、PP-M + SLANeXt 有线 + 有线单元格、PP-L + SLANeXt 无线 + 无线单元格；每组 TensorRT 冷启动、热启动各跑一遍，CUDA 跑两遍作为基线与噪声）：

- 18 次 TensorRT 运行全部成功，文档级错误为 0。
- 缓存中恰好 6 个引擎：版面、OCR 三个、有线和无线单元格各一个。热启动前后缓存文件完全不变，说明档位覆盖了真实输入形状，运行期间没有重建。
- 有线与无线单元格检测在 ORT 中的图哈希完全相同（`10041919885385002921`），SLANeXt 有线与无线也相同。这直接证实了缓存前缀修复的必要性：没有前缀时，切换到有线模型会静默加载无线模型的引擎。
- 与 CUDA 的一致率（TensorRT 对比 CUDA / CUDA 两次运行之间）：

| 指标 | TensorRT 对比 CUDA | CUDA 对比 CUDA |
| --- | --- | --- |
| 版面区块 | 0.954–1.0 | 1.0 |
| 块文本 | 0.967–1.0 | 0.997–1.0 |
| OCR 扫描件文本 | 1.0 | 1.0 |
| 表格结构 | 0.5–1.0 | 0.5–1.0 |
| 公式 LaTeX 完全一致 | 0.45–0.93 | 0.60–0.96 |

- 版面区块的差异全部是 `display_formula` 框的轻微偏移（与 CUDA 结果的 IoU 在 0.61–0.89 之间，低于 0.9 的匹配阈值），没有区块丢失或标签改变。同一个 TensorRT 二进制冷、热两次运行之间也出现过同样的偏移（仅公式文档的一组），且每页区块数量不变、只有 `display_formula` 变化，说明这些框跟随公式识别结果变化，而公式识别本身不稳定（见下条）。
- 表格和公式的差异落在 CUDA 自身的运行间波动内：PP-FormulaNet 在 CUDA 上同一二进制跑两次，公式一致率只有 0.60–0.96；公式文档中 4 个表格区块能恢复出结构的数量，CUDA 两次分别是 2 和 1，TensorRT 两次分别是 0 和 4，并非 TensorRT 系统性变差。
- **公式批大小设为 1 的对照实验**（第一组模型，两种构建各跑一遍）：PP-FormulaNet 的拒绝数从每篇公式文档 148–220 个降到 11–14 个，表格文档降到 0；TensorRT 与 CUDA 之间，表格文档的版面、公式完全一致，公式文档的公式一致率为 0.86–0.88（来自版面裁剪的细微差异）。这说明公式的大幅波动来自 PP-FormulaNet 的批量解码，与 TensorRT 无关。

**OCR 档位的优化目标**（RTX 4080 SUPER，每个形状取 30 次中位数）。动态轴原先以配置上限作为优化目标，改为常见尺寸后对比如下：

| 模型 | 推理耗时（各测试形状） | 引擎构建 |
| --- | --- | --- |
| OCR 检测：上限 4×2048×2048 → 常见页面 4×1600×1216 | 不变（差异在 ±2% 以内） | 323 s → 147 s |
| OCR 识别：上限宽度 3200 → 常见宽度 1280 | 不变（差异在 ±2% 以内） | 63 s → 44 s |

优化目标不影响推理速度，只影响首次构建引擎的时间，因此改用常见尺寸（超过配置上限时取上限）。

### 3.4 其他发现（不属于本分支，未修改）

- **PP-FormulaNet 的批量解码有缺陷。** 批大小为 4 时，大量公式在“正常输出 / 空 LaTeX / 截断被拒绝”之间随机变化，公式文档 228 个公式中有 148–220 个被拒绝；批大小为 1 时只有 11–14 个被拒绝，耗时也从 250 s 降到 96 s（一个退化的样本会拖住整批解码到最大长度）。生产配置使用 Texo，不受影响；如需使用 PP-FormulaNet，建议先把批大小设为 1，或修复批量解码。
- **同一篇公式文档的表格结构恢复不稳定。** 4 个表格区块中能恢复出结构的数量在不同运行之间为 0–4 个，CUDA 构建同样存在。
- **CLI 的 `--output` 写文件没有缓冲。** `atomic_write` 把裸 `File` 交给 JSON 渲染器，每次小写入都是一次系统调用。在 gpuhub 的 FUSE 盘（`/autodl-fs`）上，12 MB 的输出写了 10 分钟以上仍未完成。用 `BufWriter` 包装即可修复。

## 4. 代码改动

- `[runtime]` 新增 `tensorrt_cache_dir`（相对路径按配置文件所在目录解析）。各模型新增 `onnx` 表，目前只有 `tf32` 一项（仅 CUDA 生效；默认 `true`，与 ONNX Runtime 的默认一致，`false` 强制完整 FP32）。Texo 新增 `encoder_onnx` 和 `decoder_onnx`。
- 新增 `tensorrt` feature：core、CLI、server 和各模型 crate 都提供，与 `cuda` 的组织方式一致，并且隐含启用 `cuda`。
- `TensorRtProfile` 用 `ProfileDim`（`Fixed`、`Range`、`Extent`）描述各模型的形状档位。启用 TensorRT 后，凡是声明了档位的会话都会使用 TensorRT。
- TensorRT 的档位、缓存目录和 provider 构造集中在 `crates/layout/src/wasm_compat/tensorrt.rs`。缓存目录随每个配置的 backend 携带，不再使用进程级全局状态：同一进程内的多个配置互不影响，缺少目录的配置不会借用别的配置的目录。
- 缺少缓存目录时，服务启动即失败；缓存目录不可写或路径不是 UTF-8 时，同样启动失败，并在错误信息中给出路径。动态轴缺少配置上限时，启动报错并指出输入名，而不是让 TensorRT 报晦涩的构建错误。
- 日志和输出中的引擎名在 TensorRT 实际运行时显示 `tensorrt`（如 `tatr-v1.1-all-onnx-tensorrt`、`texo-transfer-onnx-tensorrt`），不再一律显示 `cuda`。
- `[tsr.cell_detection]` 现在拒绝未知字段，与其他模型配置一致。
- 引擎缓存文件名带有模型固定 SHA-256 的前 64 位、批大小和动态上限。ONNX Runtime 只按图中的节点名区分缓存，因此同拓扑的模型（有线/无线单元格检测、SLANeXt 有线/无线）原本会互相读到对方的引擎，悄悄得到错误权重的结果；不同批大小的配置也会互相覆盖引擎。加入前缀后，更换模型或批大小会构建新引擎，不会误用旧引擎。
- 带档位的模型，其预处理尺寸字面量（版面与 TATR 的 800、单元格检测的 640、OCR 的 48、320、160×80 和 32 像素对齐）整理为常量，供预处理与档位定义共用，避免两处各自修改后档位与实际输入不一致。

## 5. 偏离计划与用户决定

- 性能主指标改用独立微基准，原因见第 2 节第 2 条。
- 新增第 0 级“并发调优”。
- FP16 全部放弃，相关代码撤回。
- 用户决定：TensorRT 通过 feature 对所有模型统一启用，接受由此带来的数值差异；解码器保持 CUDA；1024 token 上限不变（解码器的位置编码只有 1029 行，无法支持更长的输出）。
- 冒烟验证后的决定：PP-FormulaNet 与 SLANet+/SLANeXt 和解码器一样，因 TensorRT 无法构建引擎而保持 CUDA。

## 6. 部署要点

- 运行时需要 TensorRT 10 的库（gpuhub 上的路径为 `/autodl-fs/data/tensorrt-10.16/tensorrt_libs`），并且要加入 `LD_LIBRARY_PATH`。ORT 1.29 不能加载 TensorRT 11。
- 首次启动会构建全部引擎，生产配置下约 4–5 分钟；启用 OCR 时，OCR 检测引擎单独还需约 2.5 分钟。之后启动直接从缓存加载。
- 更换模型、批大小或动态上限后会生成新的引擎文件，旧文件不会被使用；可直接删除缓存目录回收空间。
- 引擎与 TensorRT 版本、ONNX Runtime 版本和显卡型号绑定，升级前两者或更换显卡后要清空缓存目录。
- 推荐的 `docparse.release.toml` 改动：

```toml
[runtime]
tensorrt_cache_dir = "cache/tensorrt"

[layout]
batch_size = 4

[[formula.engine]]
worker_size = 4
```
