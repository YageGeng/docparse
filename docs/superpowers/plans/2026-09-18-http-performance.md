# HTTP 性能优化实施计划

目标：在保持现有并发与限流策略的前提下，减少大结果传输、重复解析和数据库轮询成本。

设计：完整 JSON 保持文件流；增加 gzip 和条件请求。分页使用不可变 JSON 的字节偏移索引，避免复制整份文档或每次翻页全量解析。Markdown 首次生成后持久化缓存。索引和派生文件生成使用独立可写的协调锁文件协调多实例，并与删除协调；任何文件 I/O 都不持有数据库事务。

约束：直接修改当前目录，不创建 worktree，不提交 commit；代码和普通项目文档使用英文；不修改上传并发、重试次数或增加限流；不新增手写 SQL。

## 验证结果

- Rust 服务普通测试与 PDFium 进程测试：24 通过，2 个需要额外环境的测试跳过；数据库集成测试单独运行：20 通过。两组中的普通 HTTP 性能测试有重叠，不将通过数相加。
- Clippy（所有 server targets，warnings as errors）通过；前端 TypeScript 和生产构建通过；13 份 gzip 静态资源解压后与原文件一致。
- 真实 app 后端使用 CoreML 配置，在隔离数据库中完成 3 页 PDF 上传和解析（约 3.1 秒）；浏览器查看第 1、2 页正常，无控制台警告或错误。前端代理转发的分页与 Markdown 响应均为 gzip。
- 既有 144 页结果：完整 JSON 112,616,059 字节，HTTP gzip 14,142,834 字节；两者解压后的 SHA-256 相同。第 1 页压缩后 68,843 字节，第 2 页 63,833 字节；条件请求返回 304。
- 本机 debug 服务冷建索引加首个分页响应约 2.76 秒；后续分页约 12–13 毫秒。这些数字是本机回环验证，不是生产容量承诺；首次索引生成仍需暂存整份源文件字节，之后只读取指定页。
- Markdown 首次请求生成缓存；3 页样本重复下载从约 45 毫秒降至约 2 毫秒（本机回环）。缓存、分页索引和原 JSON 的并发删除检查通过。
- 全套测试不能直接统一设置 DOCPARSE_TEST_DATABASE_URL：现有二进制配置测试会将该变量当作未知配置字段；已将无数据库测试和数据库集成测试分开执行。
- 保持上传并发、上传重试次数与限流策略不变；没有新增数据库事务；没有 commit。

## 审查修复验证

- 缓存生成和删除统一使用 `.locks/<result-name>`，不再锁定结果数据文件。锁文件以读写方式打开，删除结果后保留 inode，避免等待者和后续请求锁住不同文件；仅允许全部实例停机后回收锁文件。
- 新增回归检查先观察旧实现因结果文件锁而超时，再验证修复后缓存生成、删除与锁 inode 保留行为。存储和 HTTP 性能相关测试（含真实 PostgreSQL）共 6 项通过，Clippy 与前端生产构建通过。
- 使用真实 CoreML 配置后端解析三页 PDF；浏览器从 `page=999` 自动转为 `page=3`，第三页结果正常、无控制台错误。临时隐藏隔离环境的源 PDF 后，PDF 预览返回 503，结果页仍独立恢复到第三页；验证后恢复源文件。
- 本次未挂载 NFS/SMB 做跨客户端实测；本地回归检查覆盖协调锁与数据文件分离、读写打开及删除后的锁身份稳定性。
